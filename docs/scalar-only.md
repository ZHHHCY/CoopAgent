# Scalar 产品范围与维护基线

CoopAgent 当前的核心目标是稳定完成指挥官数值修改：理解玩家想改变的效果，定位正确数据，在正确范围内写入，并如实说明已应用结果与验证程度。

Scalar 是用户需求范围，不是底层操作白名单。生命、伤害、攻速、费用、冷却、训练或研究时间、升级加成、精通参数和已有威望系数都属于代表性请求；实现可以使用 Catalog、Upgrade、受支持的脚本参数和必要隔离。

## 完成标准

- 找对对象和数值含义，区分基础值、升级、显示数据、脚本输入和脚本输出。
- 算对目标值，区分设值、增量、比例、攻击间隔和攻速。
- 修改真实效果所使用的数据，不能用显示 dummy 或会被运行时覆盖的默认值冒充完成。
- 保持用户指定的指挥官、威望、研究和其他条件，不意外影响共享消费者。
- 覆盖请求中的每一项；未完成部分必须明确保留，不能被一份成功 Receipt 掩盖。
- 支持连续编辑、失败恢复和跨会话读取当前项目值，不依赖聊天记忆重放修改。
- 分开记录模型交付、后台应用、静态验证和游戏验证。

基础数值与威望默认分别修改。发现与结果直接相关的冲突时，在提交前用玩家语言说明；只有处理方式不明确时才询问。用户已经明确的固定值、比例或联动选择应继续沿用。

## Agent 工作流

系统提示只提供身份、通用原则和 Skill 目录。普通聊天无需 Skill；只读问题选择 `coop-query`，明确数值修改选择 `coop-scalar-change`。修改任务可以在同一 Skill 内完成必要查询，不要求先走一遍查询 Skill。

参考流程如下，它不是强制工具调用序列：

1. 判断是查询还是修改，并保留用户的目标、条件和明确排除项。
2. 用已有名册或 `entity.resolve`、`commander.get` 确认 `commanderId`、catalog 和 objectId。
3. 沿对象卡片和 `entity.get` 找到实际数值 owner；已有精确证据时跳过重复浏览。
4. 只核对会改变本次实施的当前值、用途、共享范围和条件。
5. 使用 `scalar_solve` 取得 operation、expect、value 与必要依赖。
6. 默认入口通过 `plan_prepare` 和 `plan_submit` 原子应用；启用 `change` 的配置可由后台完成同样的预检与应用。
7. 按原请求核对目标值、条件、未改项和连续编辑状态，再交付结果。

事实足够后停止查询。未知用途、空影响列表、覆盖不完整或 `runtimeVerified:false` 本身不要求继续遍历；只有具体缺口会改变答案或实现时才补查。纯查询不准备计划，不调用写入工具。

目标或效果存在实质歧义时可以使用 `target_confirm` 保存候选并等待回答。名称已经唯一、用户选择已经明确或已有结构化状态时直接继续，不重复确认。

## 职责边界

- Agent 负责理解用户效果、选择实现和说明冲突。
- 查询层提供对象、字段、继承、用途和当前工程证据。
- 请求状态保存目标、排除项和用户已经确认的选择。
- Harness 负责预算、暂停恢复和交付，不替代游戏语义判断。
- 执行器负责 Schema、真实前置条件、作用域、确定性、原子提交和 Receipt。

PatchPlan 格式见 [PatchPlan v2](patch-plan.md)，数值修改流程见 [Scalar Skill](../.opencode/skills/coop-scalar-change/SKILL.md)，具体指挥官隔离规则见 [指挥官修改策略](commander-edit-policy.md)。

## 当前能力边界

- 支持已有数值字段以及已经接入的脚本输入参数。
- 支持首轮部分交付，用户反馈后在同一项目和任务上下文中补齐。
- 不建设 Agent 自主编写或改写任意 Galaxy 函数与公式的能力；缺少可编辑参数时报告具体缺口。
- 不要求首轮穷尽全部 UI、关联对象和机制，但用户明确要求的遗漏仍是未完成项。
- Receipt 只证明工程应用，不能代替玩法效果或游戏试玩。
- `script-output` 默认值不能代替运行时公式；未找到参数不能证明整个游戏没有可编辑数据。
- 参数接口是可选实验配置，默认 workflow 保留现有 Upgrade、精通、威望条件和必要配套能力。两种配置不能同时加载。

## 开发与验收

真实失败样本用于暴露公共契约缺口，不能直接写成对象特判。修复公共语义时至少检查原样本、一个同结构变体和一个合法反例；低影响文案修改不机械扩大测试矩阵。

日常固定回归：

```powershell
pnpm test:scalar
pnpm build
```

涉及项目、UI、Rust 或地图运行层时补对应现有检查。代码测试、构建、真实 Agent 和游戏效果分别报告。命令行运行方式见 [Agent 测试接口](agent-test-interface.md)。

当前已知边界包括：弱模型可能忽略已有 no-change 证据，多字段反馈可能部分遗漏，运行时脚本输出不一定能定位到可编辑参数，参数入口尚未覆盖全部威望条件求值，UI 与游戏效果也没有全量验收。这些是如实保留的能力边界，不自动触发新一轮工具、预算或对象专用规则建设。
