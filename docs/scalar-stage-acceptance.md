# Scalar 阶段能力验收与停止扩展标准

日期：2026-09-16。状态：执行方案，尚未运行。

目的：用一次有终点的验收，判断当前 Agent 是否足以服务“修改已有数值字段”的阶段需求。通过后转入真实使用驱动的维护，不继续主动扩展机制或追求所有案例首轮成功。

依据：[产品范围](scalar-only.md)、[Agent 测试接口](agent-test-interface.md)和[题面政策](test-assets/prompt-policy.md)。启动、认证与持续监督使用测试接口；本文件规定本轮选例、反馈上限、统计和退出条件。

## 1. 本轮只验收什么

支持范围：已有 Catalog 数值、已有脚本参数、Upgrade 操作数、精通、威望系数，以及实现这些修改所必要的隔离和条件配套。正确的 no-change、部分交付后补齐、确认后继续、连续编辑都属于正常工作方式。

不要求 Agent 自主写函数或改任意 Galaxy 公式。已有字段确实无法表达需求时，应提供具体、有证据的限制并保持未修改；这是合格的边界处理，不是修改完成。

区别以下两种问题：

- 需求超出本阶段范围：例如必须改变计算公式，且无已有参数可表达。
- 支持方向内尚有缺口：例如条件数值修改因威望激活时序无法生效。不能只因能解释限制，就把该请求改判通过或移出分母。

蒙斯克现有基础贡献参数作为专用机制适配保留，不称为自主公式修改。它的 Agent 可用性参加本轮测试，运行时可靠性单列；未完成游戏验证前仍是试验能力，不纳入已验证功能宣传。

本轮不新增工具、不扩大预算、不改变模型、不修产品以迎合测试，不直接修改主工程 `game-a/build`。先冻结版本，再观察实际表现。

## 2. 何时认为“足够”

以下为本项目建议的内部阶段门槛，不是对所有 117 条或真实用户总体成功率的统计保证。

| 门槛 | 通过要求 |
| --- | --- |
| 请求达成 | 固定 25 条至少 23 条，经独立验收达到目标；每条最多两次用户反馈 |
| 实际修改能力 | 对独立确认需要修改的案例，修改完成率至少 90%；不靠 no-change 堆高完成率 |
| 修改范围 | 整个冻结版本批次，包括首轮和中间轮，没有未经授权的错误对象、形态、威望或范围外修改 |
| 诚实交付 | 没有被独立证据证实的虚报完成、虚报应用或虚报游戏验证；遗漏允许，但要如实说明 |
| 多轮链路 | 科学船连续编辑通过；泽拉图确认后继续通过；另有一次部分交付后补齐的有效证据 |
| 扩展样本 | 第 21–25 条至少 4 条达到目标，且满足同样的范围和交付要求 |
| 运行时依据 | 第 7 节主要修改路径已有可归属于当前版本的代表性游戏证据 |
| 边界处理 | 遇到真实能力缺口时有具体证据、未伪造成功；泛化超时退出不算边界处理通过 |

“最多两次用户反馈”包含确认、纠正和补全，总计最多三轮模型 start。此项比旧手册最多六次 start 更严格，仅用于本轮阶段门槛，不改变产品对真实用户的多轮支持。

没有自然发生部分交付时，不要求模型故意漏改；可复用同版本的有效多轮证据，或单列运行已存在的雷诺玩法→面板两轮流程测试。后者不加入 25 条分母，也不替代原题验收。

## 4. 启动前冻结

在新输出目录 `outputs/<日期>-scalar-stage-acceptance-<版本>/` 保存 manifest，至少包含：

- 实际模型 `deepseek/deepseek-flash`、解析后的 `workflow` profile、180/12 + 90/6 + 60/2 预算；profile 不得为空或仅写实验名称。
- Git HEAD、脏工作区清单及相关源码/提示/配置哈希、Game A 核心哈希、SC2 数据版本和数据库哈希。不能只记 HEAD。
- CSV 哈希、25 个 ID、逐条原始 prompt、反馈规则、验收条件、已知能力缺口和实验性功能。
- 本机认证仅检查是否可用，按旧手册临时传入隔离环境并清除；不记录密钥。

本批 25 条统一保留在能力分母。已知威望时序缺口或新发现公式问题可以解释结果，但不能运行后删除该题或改成成功。若确认集合/题面本身有错误，记录为集合缺陷，本轮不能给出“全门槛通过”，另行修订下一版本集合。

冻结后不要同时在主工程开发并继续创建声称属于同一版本的副本。源码变化时停止新增案例并核对版本；无法保证同版本则分批报告，不能拼接完成率。

## 5. 监督反馈与逐轮判定

复用旧手册的 `Invoke-CoopBlindRound`、观察和恢复方法。模型运行期间每 10–30 秒观察状态；后台提交未结束时继续等待，不能重复发起修改或关闭客户端中断事务。按旧手册记录 progress 和 feedback，确保中断恢复不重复发送。

每条最多首次请求加两次反馈。达到上限仍未完成记 partial / awaiting-user-confirmation / no-effective-delivery 等实际状态，不偷偷加轮；无进展的同一缺口不要反复发送“继续”。

预先规定的模拟用户回答，仅在相关问题实际出现后发送：

| 案例 | 可发送的玩家层回答 |
| --- | --- |
| 诺娃 12 询问对地/对空 | “我指防卫模式下的对地火炮。” |
| 泽拉图 18 询问比例/统一值 | 主批次固定分支 A：“保留原来不同单位之间的增益比例。” |
| 其他对象/数值问题 | 仅复述原需求已明确的内容；新增实质选择没有依据时交真实用户 |

泽拉图 B 的最终收尾证据若代码路径与当前版本一致，可用于分支覆盖；不能证明一致时，用独立副本补 B：“所有受这项精通影响的战斗单位都统一成每点 0.75%。”此分支是附加流程回归，不增加或替换第 18 条的计分。

反馈可以指出独立观察到的玩家效果遗漏，不能提供内部 ID、字段路径、函数、代码或参考计划。静态发现的问题不能表述成“我在游戏里测到”。监督者不能代替被测 Agent 修改副本。

没有要求同步的 UI 不自动升级成首轮必做项；请求明确涉及面板或每点/满点展示时按相应范围核对。未核对的显示不得宣称通过。真实遗漏允许补齐，但先前错误完成声明必须独立记为虚报，不能用最终修复抹去。

建议沿用现有分类器，必要时在报告层记录以下结果，不为此先开发新测试平台：

| 结果 | 计入目标达成？ |
| --- | --- |
| modification-complete | 独立目标、条件、关键未改项检查通过才计入 |
| no-change | 独立证据证明请求已满足且无需写入才计入，单列数量 |
| partial | 不计；反馈后全部必要项达成可更新最终结果，保留历史 |
| awaiting-user-confirmation | 不计，不能把等待当作执行失败或成功 |
| capability-gap | 不计修改达成；可单独通过边界处理要求 |
| no-effective-delivery | 不计；空 facts、泛泛超时或无具体待办不能冒充能力缺口 |
| machine-error / blocked-by-prerequisite / unverified | 不计；分别报告原因，未知不能判成正确 |

每轮分别记录模型声明、后端应用事实、独立验收结果、验证程度。收到 Receipt、模型说 complete、程序退出 0，都不能单独判通过。

## 6. 统计方式与事件处理

设 C 为三轮内真正修改完成数，N 为独立核实的 no-change 数，D 为独立核实确需修改的案例数：

- 请求达成率 = `(C + N) / 25`，通过要求 `C + N >= 23`。
- 实际修改完成率 = `C / D`，通过要求至少 90%，人数门槛向上取整。
- 当前是否已满足的状态必须以独立数据确定，不按 Agent 是否写入反推；需要修改却报告 no-change 的案例仍在 D 中。
- 有案例连是否需改都无法判断时，报告 D 的未知项，不能通过删除未知项取得实际修改率通过结论。
- 第 21–25 条单列目标达成率，至少 4/5；首轮、确认后、补全后分别列数。
- 能力缺口与安全停止不加入 C 或 N。所有 25 条始终展示，不只展示已跑或成功条目。

发现越界写入、错误对象/形态修改、虚报完成或事务破坏时，立即保存该轮证据，停止新写入型测试，允许必要的只读诊断和已有事务收尾。本冻结版本门槛不通过；后续修好也不能把该批历史事件归零。

单纯做不到、诚实遗漏、等待用户回答或机器故障，不必停止其他独立案例。网络/认证故障先检查任务是否已提交，只可在确认状态后恢复；原失败尝试保留，不能只挑成功模型运行计分。

同版本的临时基础设施故障可以有记录地恢复；产品修改则必须生成新版本。必要修复后先定向回归，再对最终版本完整运行固定批次；不能汇总多个修复版本的最好结果宣称“23/25”。一次执行任务不自动进入无限修复重跑：门槛失败时交付最多三个优先修复项，由下一次任务决定实施。

## 7. 代表性游戏验证

普通 Agent 批次不自动启动游戏。执行者先准备可复现副本、已应用计划、观察步骤和预计结果，再按当次用户授权或用户亲自试玩取得证据。当前写文档及历史探针授权不等于新游戏启动授权。

最低覆盖以下路径；这是开发验收，不是强迫每次用户改数值都跑游戏：

| 路径 | 优先案例 | 游戏观察 |
| --- | --- | --- |
| 基础值与连续编辑 | 科学船 01→02 | 最终出生满血 260/260；前轮 240 初态有产物证据；关键非目标行为保持 |
| 实际命令费用 | 扫描 22 | 成功施放扣 20 能量，不足时不可施放；费用显示与实际支付分开记录 |
| 精通与脚本参数 | 雷诺 17、泽拉图 18 | 雷诺 30 点一级步兵武器实际 10/10及面板；泽拉图不同系数单位的实际攻速与点数关系，明确分支和条件 |
| 现有条件机制 | 菲尼克斯 P1 15 | 三种战甲在 P1 的持续时间；非 P1 控制，记录提前切换等观察条件 |

既有证据可以复用，但须记录来源、实测条件及相关源码/参数未受本次改变的依据。历史“菲尼克斯复仇协议攻速通过”不能替代本表“P1 战甲持续时间通过”；静态检查同样不能替代游戏观察。

蒙斯克 20 若准备作为正常已验证功能开放，另验四等级、零/非零精通、混合人口、死亡移除、实际支持度增长、显示取整及周期更新不重复叠加。在此之前单列 experimental/runtime-unverified，不以它阻止其他已验证路径有限试用，也不宣称该参数运行时正确。

凯拉克 P2 的时序缺口需要明确标记未支持或待验证，不能从别的 P1 成功推导所有威望都可靠。若第 16 条只在静态通过，报告必须保留其运行时边界。

没有游戏授权或观察能力时，完成所有可做的静态验收并交付试玩清单，结论最多为“静态门槛通过，可有限试用；运行时门槛待验证”。不等待授权而阻塞其他工作，也不伪称整阶段全部通过。

## 8. 报告与停止条件

新输出目录至少保留：manifest、progress、feedback.jsonl、逐轮原始记录、独立 acceptance 断言、results、report，以及游戏证据清单（可以明确 pending）。复用现有文件结构，不将答案写入 blind 副本，不无必要复制完整 reference 或构建文件。

报告先给出以下四种结论之一：

1. **阶段门槛通过，转入维护**：第 2 节全部满足，已验证范围和实验性例外明确。
2. **静态门槛通过，运行时待验证**：可有限试用，列出第 7 节剩余观察，不再为此扩 Agent 能力。
3. **能力门槛未通过**：请求达成、修改率或多轮链路不够；列真实阻塞与最多三个后续修复项。
4. **可靠性门槛未通过**：存在误改、虚报或事务问题；优先修这些问题，不用总完成率抵消。

基础设施使批次无法完成时另记“验收阻塞”，提供恢复位置，不得发布完整通过率。结论同时列清楚已执行、未执行和待用户回答的数量。

通过后停止主动增加工具、公式能力、专用机制适配和预算实验。后续仅由真实使用中的误改、虚报、恢复失败、常见需求阻塞或明确的新产品需求驱动改动。允许有清楚的能力边界，不因发现一个冷门机制继续无限扩展。

## 9. 给执行 Agent 的任务

> 按本文件完成 Scalar 阶段验收。先冻结当前源码、数据和实际模型配置，按固定顺序运行第 3 节 25 条 CSV 原始请求，持续监督任务和后台提交；每例最多两次正常用户反馈。使用预设的诺娃形态与泽拉图 A 分支回答，其他新选择没有依据时交用户，不泄露实现答案。逐轮独立检查目标、条件和关键未改项，保留误改与虚报记录。不要修改产品、增加工具、扩预算或更换样本；遇可靠性阻断则保存现场并停止新写入派发。准备代表性游戏验证，未经本次授权不启动游戏。交付带明确分母、版本、反馈次数和验证程度的完整报告，并按第 8 节给出是否可以停止扩展的结论。认证或外部阻塞时保存可恢复位置，不冒充测试通过。
