# 指挥官数值修改：按真实作用范围选择实现

当前目标是稳定完成用户要求的 scalar 修改。数值需求不是操作白名单；没有“只有生命字段可用 Upgrade”或“其他字段必须克隆”的规定。先确定修改对象与适用条件，具体实现由 Agent 依据数据选择，工具不代替它做游戏设计决定。

## 不同证据对应的实现选择

- `commander.stat.set`：对指定玩家的精确数值字段应用 Set，可带真实 `prestigeUpgrade`。同一字段已有玩家修改时，读取该条件下的当前值和依赖并继续编辑。全部操作为此类时使用 `player-upgrade` 隔离策略。能写出 Upgrade 不等于已经验证所有游戏内激活和叠加行为。
- `catalog.set`：直接修改真实 Catalog 字段。只有消费者和归属证据支持时才使用 `direct-private`；字段位于本地文件、有 commanderId 或名称含指挥官，都不自动证明它是私有的。
- 必要的局部隔离：共享字段无法直接满足作用范围时，可显式克隆受影响对象、重连必要引用，并保留升级/条件/表现/生产关系。只隔离本次修改需要的部分，不默认克隆整单位或整张图。
- 必要的 Galaxy 配套：仍通过完整 PatchPlan 契约表达，明确玩家/条件过滤与前置条件。接口暂不支持某条路径，不等于原始数值需求不可能实现。

`scope` 描述用户要求影响谁，`isolation` 描述实际如何限制影响范围。后端校验这两个声明与操作是否相符；声明本身不会自动实施隔离，也不能用全局修改代替条件修改。

## 应保持的事实

基础值、某项升级的参数、指定条件下最终值是不同需求。直接改 Upgrade 数值时同时核对该项 `Reference`、`Operation`、等级与激活入口；保留未请求的这些关系。固定威望条件使用已证实的主 Upgrade ID，不把展示条目 ID 当作条件，也不把研究、Buff 或脚本条件一概当成威望。

更改生命/护盾上限时按用户意图处理出生值；价格核对真实生产命令是否覆盖单位费用；攻击间隔与攻速方向不同。未知叠加次数或条件必须保留为未知。不能为了通过预检删除条件、捏造 expect 或扩大用户请求。

连续编辑以当前工程为准，保留已有改动及 `requiredDependsOn`；不改写历史已应用计划或 receipt。克隆源对象的 Catalog expect 与玩家覆盖值不是同一事实。

## 接口与验收

当前入口使用 `plan_prepare` 预检、`plan_submit` 提交同一事务，后台负责作用域校验与原子应用。计算器用于需要数值换算的请求，调查顺序由具体证据缺口决定。操作流程见 [Scalar Skill](../.opencode/skills/coop-scalar-change/SKILL.md)。

成功依据是请求数值、适用条件、未改项与连续编辑结果。源码应用和 receipt 不等于游戏内验收；预检通过不等于已应用。失败时先看结构化诊断和当前工程，避免重复写入或遗漏已经完成的部分。

## 历史兼容

`scripts/lib/commander-edit-policy.mjs` 中的 `clone-first-v1` / `unit-life-set-v1` 是旧完整创作路线的兼容元数据，不是当前 scalar Agent 的能力许可表或必经流程。旧实现测试及已应用计划保留，当前数值查询不会把该历史建议作为新修改指令。本文不修改执行器的合法性、真实作用域、原子性或前置条件检查。
