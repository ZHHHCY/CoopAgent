# 修改指挥官数值

交付用户要求的数值效果。修改包含必要查询，无需先加载 query Skill。只读问题不调用 plan_prepare 或 plan_submit。

## 1. 明确本轮要改什么

保留每项要求的指挥官、目标、数值含义、设值或增减方式、适用条件与明确排除项。复用用户已有选择和上轮应用结果；缺少工程上下文才读 project_status。

系统提示中的合作模式对象名册或面板技能表已经唯一确定入口时直接复用。已有精确字段及含义则跳过字典浏览。缺少身份或存在候选时，带已知 commanderId/catalog 解析名称；查询用法集中在 [查询速查](../coop-query/search.md)。

只有不同玩法选择会改变本次修改、且用户尚未明确选择时，调用 target_confirm：说明当前效果、候选结果和一个具体问题。调用后本轮结束，等待回答；用户可纠正候选。字段和隔离等实现手段由 Agent 选择。

## 2. 找到实际承载它的字段

沿 objectCard 中有关的 nextQuery 定位参数，找到与请求相符的对象、精确字段和含义后停止“找字段”。精确查询或 scalar_solve 已给出所需当前值时直接复用，不为走流程双查。

按执行证据判断字段用途。展示引用、挂载或解锁条目不能单独证明实际数值由它控制；同名或 dummy 后缀也不能证明用途。已知脚本输入可作为参数，脚本输出的默认值会被覆盖。相关 mechanism 若为 supported 且 implementation.edit.available=true，复用其 target/edit；gameplay-path-pending 则记录具体缺口。

每次补查应解决影响本次实现的具体问题：字段含义、当前值、必要条件、共享范围或相互矛盾的证据。相同上下文中不重复相同查询；数据变化、新证据或分页需要时可重读。覆盖不完整和未知用途只限制能作出的结论，不自动要求完整解析或遍历所有关联对象。必要证据仍不足时交付缺口。

## 3. 核对条件与作用范围

- 区分基础字段、升级加成与条件后的结果。只核对本次适用条件及已发现的具体影响；威望入口使用 primaryUpgrade，requiredUpgrades 不证明已激活。升级加成保留真实 Reference/Operation。
- 基础值与威望默认分开修改。具体冲突先说明原效果、仅修改请求项后的结果和不确定性；处理方式未明确才 target_confirm，已有选择直接沿用。固定值或比例关系来自用户选择或机制证据，不从旧数值比值推断。不为寻找潜在冲突枚举全部研究、精通和威望。
- commanderId 不会自动隔离 Catalog 写入。按已知消费者与请求范围选择玩家数值 Upgrade、私有字段或必要的局部隔离。保留无关行为与已有修改；scope/isolation、前置条件及依赖须符合执行器契约。
- 只补实现本项效果所需的配套。例如生产费用查实际命令，整次伤害核对次数，生命上限调整核对是否也需修改出生生命。用户要求的 UI 配套纳入完成或遗漏记录；未请求的表现完善可留待反馈。

## 4. 计算、应用与交付

把已确认的目标、条件和变化交给 scalar_solve，参数见 [计算速查](calculation.md)。复用返回的 operation、expect、value、path 和 requiredDependsOn；already-at-target 无需该项写入，unsupported 按具体原因处理。

按 [计划速查](plan.md) 形成一份本轮自洽的 PatchPlan，plan_prepare 通过后 plan_submit。独立要求可部分交付，但所选部分需要的隔离、引用和条件配套一起原子提交。具体预检诊断才触发补查或修正，不改 expect、删条件或换目标来绕过错误。

提交后核对返回的应用结果与本轮覆盖项，只有结果缺失或矛盾才局部重读。task_checkpoint.summary 简述旧值 → 新值、应用状态和实质遗漏；结构化字段记录完成程度及静态/游戏验证。Receipt 证明工程应用，游戏效果仍按实际验证程度陈述。后续反馈从当前工程继续，复用已有对象和依赖。
